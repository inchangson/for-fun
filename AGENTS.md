# Tokyo travel site

- Keep this a static, Korean-language travel site. Use independent hash-route pages for each day and separate pages for extensive collections. Include real, properly licensed destination photos and maps.
- Public content: dates, sightseeing places, general descriptions, opening hours, public map and generic ticket links. Private content: actual accommodation and coordinates, flight details, personal schedule times, reservation status/codes/personal links, and family notes.
- Private data MUST be encrypted before entering the web root. `<private-detail>` contains an opaque ID only. Never hide plaintext with CSS, embed it in attributes/URLs, or put it in client source, generated assets, logs, source maps, or Git history.
- `.private/` is local-only, ignored by Git, outside Vite's web root. Never commit the source workbook, private JSON, passwords, or keys. Serve/deploy only `dist/`, never the repository root. Public data must not import private source files.
- Use Web Crypto PBKDF2-SHA-256 (600,000 iterations), a random 16-byte salt and AES-256-GCM with a fresh 12-byte IV. Do not create custom cryptography. Authenticated decryption must fail closed.
- A single global toggle unlocks all private elements. Hold decrypted data only in tab memory across internal navigation. Never store plaintext/passwords/keys in localStorage, sessionStorage, URLs, analytics, or logs. Clear password/key references after use. OFF, reload, pagehide, and back-forward-cache restoration lock the app; cancel pending unlocks so stale results cannot reveal content.
- Render decrypted text with textContent, never innerHTML. Validate private links as HTTPS; create href only after unlocking. Remove plaintext and href on locking. Do not promise forensic memory erasure or revocation of previously viewed data.
- Maps, photo names, metadata, public notes, and area labels must not reveal private accommodation or personal routes. Maps show public sightseeing only. Never request a private map position from tile providers.
- Self-host application JS/CSS. Per user preference, use direct Wikimedia image URLs with attribution and a loading-failure fallback; do not require photo downloads. Preserve image license credits and map attribution. Use official sources for opening hours/exhibitions, record verification dates, distinguish proposals/estimates from confirmed bookings, and retain original alternatives. Do not purchase tickets or change existing reservations.
- Preserve booking/flight constraints when adjusting schedules. Separate local checklists from shared trip data; only checklist boolean states may persist in browser storage.
- On changes touching privacy/build behavior, run crypto and artifact-leak tests plus browser unlock/lock/reload/navigation/race tests. Test mobile layouts and static subpath hosting.
